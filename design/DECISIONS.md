Decisions about anything a user sees or types: the owner's answers to the previews in
`design/preview/`, and — since the owner put the project under Claude's management on
2026-11-25 — the choices Claude makes where the approved design is silent. Each row gives
the reason, so a later session can tell a considered choice from an accident. A decision
here is changed by adding a row, not by building something different.

| 2026-11-25 | Graph semantics, as the correctness oracle checks them (`oracle/SEMANTICS.md`, Q1–Q13) | On a directed graph `degree` is the number of distinct neighbours in either direction — the degree in the undirected projection — not `in_degree + out_degree` as NetworkX and igraph define it (a reciprocal pair is one neighbour). Core numbers, triangles, clustering and transitivity of a directed graph are computed on that projection, which sums the events of both directions. A kept self-loop adds 2 to the undirected degree and 1 to each of in- and out-degree; repeated rows of a pair count once, with weights summed for PageRank and the minimum taken for shortest paths. Clustering at degree below 2, transitivity without a triple and modularity without edges are 0, never NaN. A component's internal label is its earliest node (the API then numbers components by size). Traversals follow out-edges unless `direction=` says otherwise; an unreachable node has no value. PageRank is the fixed point, whatever the iteration count. PageRank and core numbers with kept self-loops are defined by #36. *One projection for everything that ignores direction (communities, k-core, triangles, `degree`, hubs), so the numbers a user sees on one graph agree with each other; where the libraries disagree with each other we follow the one that returns a number.* | decided by Claude |
| 2026-11-25 | How the project is run, for speed | After a discussion with the owner: up to about eight agents at once on every ready issue; official measurements batched into short windows while development continues outside them; decisions from interleaved A/B runs, an empty machine only for published numbers; review in three tiers by risk; a thin end-to-end slice first, with a dogfood pass at each milestone; code kept small, a test audit with `cargo-mutants` at each milestone. Rules in `CLAUDE.md` §4 and §6. *The owner asked for faster execution without losing quality, and worried about code and test bloat and about process for its own sake.* | decided by Claude, discussed with the owner |
| 2026-11-25 | Graph semantics, the cases left to #36 (`docs/spec/graph-semantics.md`, PR #145) | One principle: a kept self-loop is a pair {v,v} of weight w, entering the adjacency as A[v][v] = 2w on an undirected graph (and on the undirected projection) and w on a directed one. **Volume and flow measures** count it through that matrix — degree (+2, Q1), strength, PageRank (as igraph and PRPACK; NetworkX counts w), modularity (as both libraries; Leicht–Newman and CPM likewise), and the quotient graph, which carries input loops on its diagonal. **Cohesion and reachability measures ignore it** — core numbers (NetworkX refuses loops; igraph would make a lone looped node a 2-core), triangles, clustering and transitivity with k′ = neighbours other than itself, components, traversals. Also: loops are treated before duplicates; an identifier whose only rows were dropped loops stays as an isolate; `duplicates="sum"` analyses as "events" (multiplicity from the `edges` column) and `window()` on it is `Unsupported`; a pair's weight is the exact sum of its events rounded once to f64; exact integer/decimal sums stay exact (decimal128/256), overflow is `InvalidInput`; column statistics at build are count, nulls, NaN, min, max, sum and the largest pair multiplicity; reported sums (degrees' `weighted`, `neighbors()`, `to_scipy()`) never refuse; `to_scipy()` puts w on the diagonal so it round-trips with NetworkX. *Consistency: modularity must be equal before and after Louvain/Leiden aggregation, which turns a community's internal edges into a loop — so input loops must count the same way; a k-core is about ties to other nodes.* | decided by Claude |
| 2026-11-25 | Memory-mapped files are read through a safe constructor | `everygraph-io`'s `MmapSource` stays a safe API, under a recorded invariant: Everygraph maps only files it wrote itself and never writes again (graph files, spill files, stores), and no writer — another process or this one — may modify or truncate a file while it is mapped; violating it is undefined behaviour or SIGBUS, and is not enforced against other processes. Inside the process the sinks refuse to create, truncate or write a file (by device and inode) that a live `MmapSource` holds. The SAFETY comment and the docs state exactly this. *A safe map is the convention of the Rust ecosystem for read-only data files; making every caller `unsafe` would push `unsafe` into kernels, which the project forbids, while the in-process guard closes the one hole safe code in this workspace could open (review of PR #151).* | decided by Claude |

Publishing also ends the Actions-minutes problem (public repositories use GitHub-hosted runners, macOS, Windows and ARM included, at no cost). | 2026-11-25 | Identifier columns: hex prefixes, UUIDs, stray keys | Hex keys come back lowercase, with `0x` when the input used a prefix (`0x` or `0X`) and with none otherwise; UUIDs come back lowercase, hyphenated, and are looked up in any case. A key that does not fit the column's detected kind (an empty or `"0x"` address in a hex column) is an **invalid row**, reported with its line like any other, not a reason to reinterpret the whole column as text; `ids="string"` keeps every key as text. *One stray value must not change the identity of every node (review of PR #158: one bad key turned 155,184 nodes into 205,047).* | decided by Claude |

| 2026-11-25 | The map's super level | Built when the partition T needs more than 63 communities to cover 90% of the nodes; on a rebuild of the same dataset, hysteresis — switched on above 72, off below 56, otherwise the previous decision kept. | 2026-11-25 | Label propagation follows LDBC CDLP | Label propagation (#65, `plan/issues/m4-09-label-propagation.md`; its public name is chosen when it is built, `docs/api-sketch.md` § 7) is synchronous label propagation with LDBC Graphalytics CDLP semantics: each node's initial label is its position in the original key order, and ties go to the smallest label. It is never a low-budget fallback for Leiden. A relabelling of stored ids (#146) must keep id-dependent semantics on the original ids: CDLP labels and ties, min-label components, BFS from a given source. *Our earlier tie-break by label hash differed from the only standard deterministic LPA, so our results could not be checked against LDBC's reference outputs. CluStRE, the earlier fallback candidate, has a 10-minute wall-clock cut-off in its local search, so it is not deterministic (`docs/research/README.md` A5; `docs/research/memory-bounded-algorithms.md` addendum item 17; `sota-communities.md` § 3).* | decided by Claude |
| 2026-11-25 | Memory maps and I/O errors (amends the safe-mmap row above) | The planner maps only files on local block devices; every other file (network or removable file systems, FUSE) is read through `FileSource`. The SAFETY comment and the docs of `MmapSource` add: a media or device error under a map ends the process with SIGBUS, where `pread` returns EIO. Warming regime 1 uses `MADV_POPULATE_READ` where available, which returns an error instead of raising a signal. *The recorded invariant covered modification and truncation, not I/O errors (Crotty et al., CIDR 2022 § 3.3, as read in `docs/research/sota-io-memory.md` § 3; `docs/research/README.md` A8).* | decided by Claude |
| 2026-11-25 | The map's keyboard model | **Arrow keys move through the structure** — down into a region, up to its parent, sideways between siblings — as `design/preview/style/foundations.html` § 9 says ("arrow keys move between regions, Enter opens one, Esc goes up"); **Shift+arrows pan**. The single-key shortcuts `/ + - 0` act only while the map has focus, never at document level. In the Jupyter widget, where Esc is also JupyterLab's "command mode", the keyboard is never trapped in the map: Esc at the top level, or a documented key, leaves the map's focus (WCAG 2.1.2). *The two approved previews contradicted each other: `viewer.html` (around line 1865) makes arrows pan and binds `/ + - 0` for the whole document, which WCAG 2.1.4 allows only for shortcuts that can be turned off or remapped or that act only on focus. The written rule of § 9 wins, because it is the one a screen-reader route through the hierarchy needs (`docs/research/sota-human-factors.md` § 3, challenge 3; `docs/research/README.md` H3). `viewer.html` is updated to this model when #72 is built; #72 and #76 build to it.* | decided by Claude |
| 2026-11-25 | Approximate results | An approximate result is marked in the result itself, in the places a result cut short is (`docs/api-sketch.md` § 2.5): **`.approximate`** is `True`, and **`meta["approximate"]`** holds `method`, `seed`, `samples`, the guarantee's kind, `epsilon` and `delta` or the relative standard deviation, and `runs`; the same keys go into the provenance record's parameters, and the table's footer says it. Precision parameters (HyperLogLog registers, ε, δ, the sample schedule) are **never derived from the memory budget or the thread count**. Where no bound is proven — HyperBall's harmonic and closeness centrality — the result says so and prints only an empirical spread over runs. *The result-cache key leaves out `memory` and `threads` because they cannot change a result (`docs/api-sketch.md` § 2.8); a precision chosen from the budget would make two budgets return different bits under one key. And promise 3 ("trust it") needs the guarantee printed with the number, not in the documentation (`docs/research/sota-approx-rust.md` § 3 A, challenge 4; `docs/research/README.md` R4). No operation in 0.1 is approximate; this fixes the names § 2.5 left open for #52.* | decided by Claude |
| 2026-11-25 | Writing a graph file again: the container's commits | A graph file is written again only by the container's update protocol (`docs/spec/eg-container.md` § 8, § 11), and only in two places: header block B (bytes 4096–4223 or 0–127) and bytes at or past the committed end; the file is never shortened below a committed end, and `compact` writes a new file. In the process, `everygraph_io::FileSink` refuses a mapped file like the other sinks, so a graph is committed to only after its maps are dropped. A reader in another process that maps the *whole* file would see the 128 bytes of the header block change under its map, which the row "Memory-mapped files are read through a safe constructor" does not allow: readers that map a graph file are to map only the range 8192 … committed end, which no commit changes, once `MmapSource` can map a range (issue `m2-21-range-maps`); until then, committing to a graph that another process holds mapped is outside the invariant. A commit also shortens the file to the new committed end, which can cut off an uncommitted tail that a whole-file map of another process covers (`SIGBUS` if touched). Within the process `FileSink` holds its file alone; one writer across processes is issue `m2-22-single-writer-lock`. *Appending results to the graph (`docs/api-sketch.md` § 2.8, ux-contract C-2) is a write to a file Everygraph maps; the invariant has to say exactly which bytes it touches.* | decided by Claude |
| 2026-11-26 | Masked and materialized views give the same bits | D14's promise holds for views: a deterministic kernel returns the same bytes on a view run as a mask and run materialized. A materialized view renumbers its nodes densely, keeps graph order, stores the map from its new ids to the parent graph's ids, and runs every result-bearing reduction over the parent graph's node blocks through that map (ADR 0028, A2); a view saved with `save()` keeps the map. *Reduction blocks are a function of the graph; with new ids alone, a materialized view would sum floats over other node ranges than its mask, and the planner's choice between the two would change the answer. #93 (`plan/issues/m7-04-views.md`) builds it and tests it on PageRank.* | decided by Claude |
| 2026-11-26 | How identifiers are read: `ids=` | `eg.read(…, ids="auto")` by default: the kind of the identifiers (integers, hexadecimal, UUIDs, base58, fixed-size binary, else text) is detected from a sample of the first keys, and a key that does not fit is an invalid row. `ids="string"` keeps every key as text, as written. On the command line: `everygraph ingest FILE --ids auto\|string`. *The row "Identifier columns: hex prefixes, UUIDs, stray keys" and the dictionary of #34 (`everygraph_ingest::ids`) already use `ids="string"`; this names the option and its default where users type it (`docs/api-sketch.md` § 3.1, § 5.1).* | decided by Claude |
| 2026-11-26 | The `compact` command | `everygraph compact FILE` writes a copy that holds only what the newest commit uses and replaces `FILE` in place: the copy is written as `FILE.partial` and renamed over `FILE` once durable. `--out NEW` writes the copy elsewhere and leaves `FILE` unchanged. No Python method in 0.1. *ADR 0027 makes `compact` the way to reclaim replaced results; in place is what a user who runs it on a full disk wants, and `.partial` plus rename keeps a stop harmless, as for every other write (ux-contract C-1).* | decided by Claude |
| 2026-11-26 | A second writer on a graph file is refused | A process that tries to write a graph file that another process is writing gets `ResourceBusy`, which names the file (and the other process where the platform tells). It does not wait. *A wait with no end in sight is a hang to the user; a refusal says what is happening, and the user runs the command again. The lock is #205 (`plan/issues/m2-22-single-writer-lock.md`); `docs/api-sketch.md` § 2.9 says the same.* | decided by Claude |
| 2026-11-26 | Range maps of a graph file (amends "Writing a graph file again: the container's commits") | A graph file is mapped by range: `8192 … committed end` of the commit the reader opened (`Container::stable_range`, `everygraph_io::MmapSource::from_file_range`), and the container read through it keeps the header and table read before the map (`Container::with_source`), so that a commit in between cannot make the two disagree. No commit by any writer that follows the container's protocol changes those bytes or truncates the file into them, so such a map is safe against commits by this process and by other processes; a whole-file map of a graph file is not, and is not used for one. In the process, on Unix, `FileSink` no longer refuses a mapped file: it refuses each write or length change that would reach a mapped range (`ResourceBusy`), so a process commits a result to a graph it holds mapped; a map reads the file's length and registers its range in one step. On Windows there is no such guard. Still outside the invariant: a writer that does not follow the protocol (`std::fs`, another program), and `Writer::update_recovered`, which writes over a newer commit on purpose. *Results are kept in the graph file (`docs/api-sketch.md` § 2.8) and the in-RAM mode is a map of that file (D11); the protocol already leaves the range alone (`docs/spec/eg-container.md` § 11). Tests: `a_process_commits_a_result_to_a_graph_it_holds_mapped`, `another_process_commits_100_times_to_a_file_this_one_maps_by_range` (#204).* | decided by Claude |
| 2026-11-26 | A structure-only export | `everygraph export GRAPH --topology-only --out FILE` writes the edges without any property column, so that a user can share a failing case (#106). It is never called "anonymized": the command prints a one-line notice that structure alone can identify people. *Narayanan and Shmatikov re-identified users of an anonymized graph from its structure (`docs/research/README.md` H7); a word that promises privacy would be false.* | decided by Claude |
| 2026-11-26 | `everygraph verify` reports on standard output | The report of `verify` is its result, intact or damaged, so it goes to standard output: `✓ FILE is intact.` with what was checked, or `✗ FILE is damaged: N problems.` with one line per problem (the section, then what is wrong), the ways forward and `Nothing was changed.`; exit status 0 or 5. With `--json`, the verify document (`urn:everygraph:schema:verify:1`, `docs/api-sketch.md` § 5.3) in both cases. A file that cannot be read at all is an `IoError` on standard error, status 1. A header block that the file does not read from and that holds no valid header is a **note**, not a problem: a commit cut short leaves exactly that, and no reader can tell it from damage. *A script that runs `verify` wants the report where results go, and "damaged" is an answer, not a failure of the command; calling a cut-short commit damage would make a file that C-1 promises is complete fail `verify`.* | decided by Claude |
| 2026-11-26 | Reading the command line | By hand in `everygraph-cli` (`src/main.rs`), with no argument-parsing crate, while the command has one verb (`verify`) and two flags. #98 chooses the parser for the full command set. *A dependency for three words is more code to audit than the words; the help text and the usage errors follow `docs/api-sketch.md` § 5 either way.* | replaced by "Reading the command line, with `clap`" |
| 2026-11-26 | A lost newest commit | When the newest commit of a file cannot be read — its table of contents is damaged, or its header block is damaged or was cut short while its table is whole — and the file reads as the commit before, `everygraph verify` prints a warning on standard error that names the lost generation ("The newest commit, generation N+1, could not be read." and "The file reads as generation N, which is whole.") and exits with status 0; with `--strict` it exits with status 5. The verify document carries `lost_generation`. The note rule of the row above stays for a header block that names no commit whose table is whole. *A commit cut short and a damaged newest commit leave the same bytes, and ux-contract C-1 promises that a file left by an interrupted commit passes `verify`; but a user who saw generation N+1 committed must be told it is gone, and a script that cannot accept that asks for `--strict` (review of PR #212, S1; decided by the coordinator).* | decided by Claude |
| 2026-11-26 | Reading the command line, with `clap` | `everygraph-cli` reads its command line with `clap` (derive), one struct per command, and keeps no parser of its own. The help texts stay the commands' own, in the layout of `docs/api-sketch.md` § 5.3 (`clap` prints them as written); `clap`'s errors become usage errors in the words and shape of `docs/ux-contract.md` § 6.1 (`Unknown option --deeep.`, `--duplicates takes events or collapse or sum, not some.`), exit status 2, and the error document with `--json`. *Six commands and some thirty options outgrew hand parsing: `clap` gives every command the same handling of values, `--name=VALUE`, `--` and conflicts, with less product code; the benchmark harness already depends on it (sweep of PR #228, decided by the coordinator).* | decided by Claude |
| 2026-11-26 | Short options | Three, the same on every command that takes the option: `-o` for `--out`, `-m` for `--memory`, `-t` for `--threads`; and `-h` for `--help`.
