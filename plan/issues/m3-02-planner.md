**Why.** "Adapts to any hardware" is the planner. The lab gave it a simple core rule: **choose the regime by the size of the kernel's O(n) state, not by the graph's size** — if the state fits the budget, run on mmap; streams are for a hard bound.

**Rules to implement (each from a measurement)**
- State does not fit the budget → refuse with the minimum budget. The planner may switch by itself only between strategies that give the identical result (e.g. streaming union-find instead of the in-memory WCC kernel); a variant that changes the result (f32 state) is never substituted: it is offered in the refusal as a way forward, and only where it exists (`design/DECISIONS.md`, 2026-11-25, "What 'repeatable' promises")
- Decode tier (ADR 0004): compressed for every kernel; build the raw cache only if R + S ≤ M with headroom and the session repeats traversals or point lookups past the break-even (arithmetic on #118's measurements: about 6–7 BFS runs at 16 threads, 280–970 shortest-path queries, 0.85–8.7 M neighbour lookups, orkut to Friendster; for the production BFS with parents, decoded into new arrays as the planner does, 2.3–5.6 runs on orkut and 1.8–3.1 on lj, exploratory, PR #249, until the official `planner-*` run of `bench/specs/edge-map.toml`); a BFS cut at a depth never builds the copy; never for PageRank, WCC, k-core, triangles, Leiden; if raw does not fit and compressed does, stay compressed (raw through mmap 1.2–5.4× slower on scans)
- Budget below the compressed size → semi-external streams (fixed RSS 1.3–1.5 GB on Friendster) or mmap under pressure (same speed, RSS = limit); prefer streams when a hard bound was requested or storage is not fast local NVMe
- Threads per kernel class: physical cores for memory-bound scans (PageRank, components, BFS and k-core gained nothing from 16 → 32 threads); all hardware threads for compute-bound kernels (triangles 2.51 → 1.46 s, Louvain on orkut 0.88 → 0.65 s); fewer for tiny inputs (parallel parse of a small file was slower at 32 threads)
- Thrashing is a refusal, not a slow death (added 2026-11-25, `docs/research/sota-io-memory.md` C3; rule measured by {{#m2-19-allocator-policy}}'s monitor experiment): when file refaults in one pass exceed about one file's size, the stage is stopped with a refusal that names the regime that would work. The tracer ran 460–648 s before being killed (`bench/results/tracer/20261125T122609Z-3e764d115d86.jsonl` rows 9, 11–12)
- Random access under pressure (ADR 0029, proposed, from {{#m1-15-mmap-hints-block-cache}}): advice is chosen **per phase** from a working-set estimate per phase. A random-access phase whose working set exceeds its budget gets `MADV_RANDOM`, and the block cache of {{#m2-23-block-cache}} (`BlockCache` over a `ReadPool`, its size taken from the budget) only where a measured comparison at equal memory shows the cache reads fewer bytes (ADR 0029, "The cache as built"); no kernel of the planner has such a phase yet (Leiden is not a planner operation); the advice is reset to `MADV_NORMAL` before a scan phase (whole-run `MADV_RANDOM` made Leiden's level-0 aggregation scan 1.44–1.58× as long); `MADV_RANDOM` is never set when the working set fits (the layout under 32G, where the CSR fits: 2.9× slower and 8.7× more bytes read, because global reclaim took the advised pages; one run, shared machine). Under 16G the same advice cut the layout's bytes read to 0.16× and Leiden level-0 local moving and refinement to 0.15× (8G) and 0.07–0.09× (4G) (`lab/m1-15-mmap-hints-block-cache/results/`; bytes from `/proc/self/io`, exploratory, independent of load). The plan shows the advice per phase. A larger gain than any pager comes from the access order: storage-order visits ({{#m1-14-relabel-at-ingest}}) and, for the layout, a store renumbered by the hierarchy. Files that are not on a local block device are never mapped (`design/DECISIONS.md`, "Memory maps and I/O errors")
- Views: mask or materialized by a rule that {{#m7-04-views}} derives from measurement (number of passes, memory budget and selectivity; the earlier "~25%" threshold was not a measurement — ADR 0010). A provisional rule is in place (`planner::view_form`, PR #315)

**Scope**
- [ ] Hardware probe: physical cores, RAM available, cgroup limits, storage type and a quick bandwidth probe
- [ ] Per-kernel cost model: O(n) state bytes, scans per iteration, random vs sequential access, and **bytes written** (added 2026-11-25, `docs/research/README.md` M5; `docs/research/sota-measurement.md` § 3.3, challenge 9): a write costs λ reads, λ = read rate ÷ sustained write rate, about 3.9 GB/s ÷ 1.4–1.6 GB/s ≈ 2.4–2.8 on the lab drive when sustained and about 0.7 inside the burst; an intermediate is materialized only if it is re-read more than λ times, otherwise re-read or recomputed (Viglas, PVLDB 2014, simulated NVM, single thread). Bytes written are shown in the plan (P-9). Wear is not a rule: a Friendster pipeline writes about 80–100 GB (four measured parts from different runs, summed: an estimate), about 0.0083% of a 2 TB 990 PRO's rated 1,200 TBW (arithmetic). A phase's spill files are deleted together and written as large sequential appends
- [ ] `explain()` output per {{#m0-12-ux-contract}}; user overrides for every choice
- [ ] Lookup before compute: a result on the whole graph is looked up with `Container::find_result` before it is computed and stored with `Writer::add_result` after ({{#m2-12-artifact-cache}}); `explain()` shows the reuse, the phase is shown as `kept` and `meta["cached"]` is `True` (`docs/api-sketch.md` § 2.8)
- [ ] Plan recorded in result provenance
- [ ] Plans and refusals as `docs/ux-contract.md` § 3: documents valid against its closed plan, error and event schemas; only ways forward that exist (P-15); a budget above the machine's memory is a usage error (P-16), one above free memory is honoured with a line (P-17), memory-backed scratch counts against the budget (P-18); estimate and actual in each result's provenance (P-9)

**Acceptance**
- On the lab machine the planner's choice is within 10% of the best manually chosen configuration for PageRank, WCC and BFS on orkut, twitter-sym and Friendster at budgets of 2, 8, 16 GiB and unlimited
- On orkut and twitter-sym the planner switches to the decode tier after the break-even count of BFS runs, not before
- It never selects a plan that is then OOM-killed ({{#m3-10-no-oom-ci}})
- For every kernel, the result hash is the same in each regime the planner can choose (in memory, edges on disk, state on disk), tested by forcing each regime on a tier-1 graph (`design/DECISIONS.md`, 2026-11-25, "What 'repeatable' promises")
