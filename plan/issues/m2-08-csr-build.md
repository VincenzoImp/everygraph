**Why.** This is the "open anything fast" promise. The lab pipeline (parse → rank directory → relabel + partition into ≤ 2,048 buckets → per-bucket sort/dedup → ordered commit) already uses one code path for both regimes and is byte-identical to the reference in every mode.

**Build plan (amended 2026-11-25 from the literature review, `docs/research/sota-ingest-query.md` C1, C7 and `docs/research/sota-io-memory.md` C4, C6; decision B7 in `docs/research/README.md`).** Every run of the lab pipeline writes temporary data even when it is not needed: 45.1 GB per Friendster ingest at a 32 GB budget and 55.4 GB at 8 GB (cgroup `io.write_bytes`; 29.6 / 39.9 GB of it temp; FINDINGS § B1, ADR 0026), and on this drive the ingest is bound by bytes written. The build therefore takes the path that writes least:

- [ ] **Step 0, before the production code: an interleaved A/B in the lab crate** (`lab/b1-core`), Friendster, harness warm-up protocol (ADR 0026), at 32 GB and 8 GB, uncompressed output for both sides: the current pipeline against the two paths below. Metrics: wall time, cgroup `io.write_bytes`, PSI io stall, anonymous peak. The production build takes the variant that writes fewer bytes without being slower; the result goes to FINDINGS with its result file. Anything that loads the graph runs under `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0`
- [ ] **No spill when the targets array fits** (ingest C1; the two-pass structure of PIGO): pass 1 counts degrees by original id and builds the rank directory; pass 2 scatters targets into an O(m) array (Friendster: 3.6 B entries × 4 B = 14.4 GB, which fits a 32 GB budget); then each list is sorted and deduplicated, which restores the canonical order whatever order the scatter wrote; then the streaming encoder. Bytes written would fall from 45.1 GB to about the output (~10 GB); estimate 15–22 s at 32 GB from our own phase times, which is ADR 0026's "≤ 20 s" threshold (an extrapolation, not a measurement). The planner rule: targets array plus degree and rank arrays fit the budget with headroom → this path
- [ ] **Under 8 GB, hybrid RAM/file buckets** (io-memory C4a; DuckDB's policy): buckets stay in RAM while they fit and only the overflow spills; when memory runs short, later buckets are demoted first, so the smallest uncommitted bucket always keeps its reservation (no deadlock; the rule M1-02 already uses for aggregation). Re-reading the input once per source range instead of spilling is the alternative to measure when the input is plain text in the page cache
- [ ] **Exact bucket boundaries from the degree counts of pass 1**, not sampled quantiles (ingest C7): balanced and deterministic, and they never change the canonical output. Replaces the lab's "partition by original-id range using sampled quantiles"; still relabel inside the per-bucket sort, which removes the separate spill pass (22 GB of temp traffic on Friendster) and balances skewed buckets (lj's largest bucket was 10× the mean)
- [ ] **6-byte spill records** (io-memory C4b): the source stored as an offset inside its bucket's range (about 32 K nodes per bucket on Friendster, so 16 bits) — −25% of the dominant temp volume
- [ ] **One radix sort per bucket on a packed key** (io-memory C6) against today's counting sort followed by `sort_unstable` per list, as an interleaved A/B on the bucket phase only (Friendster buckets in RAM). Sequentially, IPS4o's paper (TOPC 2022, Table 1, their machine) measures std::sort 2.4–3.4× and BlockPDQ (the lineage of Rust's `sort_unstable`) 1.5–2.7× slower than its radix sort on uint32, uint64 and 16-byte pairs; per-list sorts on social graphs are tiny, so the gain holds only if a whole bucket is sorted at once. It matters where the build is CPU-bound (in-RAM lj and orkut), not for the write-bound 8 GB ingest. The output is identical (the key order is total). Where `duplicates="events"` keeps several rows of a pair, the key includes time and input position, so the stored order (neighbour, time, input order) is restored whatever order the scatter wrote
- [ ] Temp storage: page-cache-backed files now; large sequential per-thread logs with an extent index if direct I/O is wanted (small appending O_DIRECT writes cost ~0.9 ms each on ext4)
- [ ] Output through the aligned-block writer ({{#m2-02-io-layer}}); write directly in the compressed format ({{#m2-03-adjacency-codec}}) with an encoder that runs under the budget — the #118 encoder holds input and output in RAM (Friendster about 14 GiB raw + 9.8 GiB compressed); encode 0.064 / 0.168 / 3.41 s at 16 threads (lj / orkut / Friendster) plus 4.77 s write with fsync on Friendster
- [ ] Budget-driven: the path, bucket count and buffer sizes derived from the memory accountant ({{#m2-04-arrays-accountant}})

**Scope**
- [ ] Undirected (symmetrized) and directed builds
- [ ] Carry property columns through the sort (weights, timestamps) ({{#m2-10-property-columns}})
- [ ] Deterministic output independent of thread count
- [ ] Treatment order per row: read, self-loops (drop or keep), duplicates (`events`; `collapse` keeps the first row in input order; `sum` merges), stored; an identifier whose only rows were dropped loops is still a node, an isolate (`docs/spec/graph-semantics.md` § 2.3)
- [ ] Pairs in the adjacency, events beside it (ADR 0028; `docs/spec/eg-adjacency.md` § 3.1, `docs/spec/graph-semantics.md` § 2.5): group the events of each pair after the sort; each list holds each neighbour once, in increasing internal id of the neighbour (graph order until a renumbering, {{#m2-24-bp-ordering}}); a pair's events are ordered (time, input order), nulls of time last, the same at both ends of an undirected pair; the in-adjacency the same
- [ ] Write the `.events` section (kind 5, `<name>.events`) of each adjacency — out, and in on a directed graph — when some pair has more than one event, and none otherwise, setting index flag bit 1 exactly when it exists: an Elias–Fano sequence of per-entry event offsets (`len = entries + 1`, `U = events`), built streaming beside the entry offsets; the reader checks of `eg-adjacency.md` § 5 for it (header and length with checked arithmetic at open, whole-section checks at first use) and the cross-section checks (out and in both or neither, equal `events`; name and kind 5 agree; per-event columns have `events` rows); it belongs here, not to #30
- [ ] Per-event columns carried in event order (indexed by event offset); per-pair aggregates computed from each pair's event range (the exact pair sum of `graph-semantics.md` § 4.3, and what #37 decides) and written per pair (indexed by entry offset) ({{#m2-10-property-columns}})
- [ ] Correct the doc comment of `AdjacencyIndex::entry_offset` (`crates/everygraph-format/src/adjacency/index.rs`: "Edge-indexed columns are indexed by it"): per-pair columns are; per-event columns are indexed by event offset
- [ ] Ingest report in the provenance: `rows`, `rejected`, `dropped.self_loops`, `dropped.duplicates`, `merged`, `edges`, kept `self_loops`, `repeated`, `pairs`, `nodes`, `isolates` (`docs/spec/graph-semantics.md` § 2.8)
- [ ] Scaling work: the prototype scales only 3.4–4.9× from 1 to 32 threads on small graphs. The realistic ceiling is about 8×, not 32×: the published sort ceiling on a 16-core single-socket desktop is IPS4o's 8.37× (Ryzen 9 3950X, 2^30 u64 keys, their machine), because permutation is memory-bound. First a per-phase profile at 1, 2, 4, 8, 16 and 32 threads on orkut in one harness run (times and GB/s per phase), to find the serial phases or page faults: orkut moves about 8–10 GB in 0.78 s, about 11 GB/s, far below bandwidth (`docs/research/sota-ingest-query.md` § 3, C7; arithmetic by the review)
- [ ] A streaming adjacency encoder: #30's `encode` takes a CSR in memory and returns the data part as one `Vec` (10.5 GB on Friendster) plus 8(n+1) bytes of record lengths, allocated fallibly but outside DESIGN D2. Here: take lists in node order, write records block by block to a sink in segments of at most 2 GiB, reserve every buffer through the accountant ({{#m2-04-arrays-accountant}}), build the two Elias–Fano sequences at the end from per-node record lengths and degrees kept in segmented arrays

**Acceptance (lab machine, idle, plain text)**
- lj ≤ 0.5 s; orkut ≤ 1.0 s; Friendster ≤ 25 s at a 32 GB budget and ≤ 60 s at 8 GB with peak RSS ≤ 4 GB, writing the default format, measured under the harness's warm-up protocol (sustained drive write rate, ADR 0026), fsync reported separately and bytes written reported next to the time (baseline by addition: 36.97 s sustained build at 8 GB, `bench/results/headline/20261125T114658Z-0ffe756ac9ac.jsonl`, + 3.4 s encode at 16 threads from #118 = 40.4 s before the write; at 32 GB 29.06 + 3.4 = 32.5 s, so ≤ 25 s needs the temp-traffic reductions above)
- Output identical for budgets 0.25 GB … 32 GB and thread counts 1 … 32
- Out-of-core NVMe traffic for Friendster at 8 GB reduced from 128 GB to ≤ 90 GB
- An input with repeated pairs read with `duplicates="events"` is written and read back: on every oracle graph with repeated pairs, each entry's multiplicity `ev[e + 1] − ev[e]` equals the number of rows of its pair, `Σ` multiplicities of the out-adjacency equals `edges` on a directed graph (`2·edges` minus kept loop events on an undirected one), and a graph without repeated pairs, or read with `collapse` or `sum`, has no `.events` section; the size of the `.events` section is reported in bits per pair on one temporal graph (`eg-adjacency.md` § 7 gives the arithmetic it is checked against)
- With a budget at which the targets array fits (Friendster at 32 GB), the build writes no temporary data: cgroup `io.write_bytes` equals the output plus its metadata, reported next to the time
- Step 0's A/B recorded in FINDINGS with its result file before the production path is chosen
- On every oracle graph and every `self_loops` × `duplicates` option, a test checks `rows = rejected + dropped.self_loops + dropped.duplicates + merged + edges` and `edges = pairs + repeated` (`docs/spec/graph-semantics.md` § 2.8; shared with #40)

**Pointers.** `lab/b1-core`, FINDINGS § B1 "Where the time goes".

**Second research wave (2026-11-25, `docs/research/README.md` M1, R5).** The ranged writes of the build (list records by offset ranges) go through the safe helpers of {{#m2-28-par-scatter}}, not through a raw-pointer scatter copied from the lab. The drive rate behind the Friendster targets may be this host's, not the drive model's: the "~10 GB burst, then 1.4–1.6 GB/s" of ADR 0026 was measured on a drive mounted without `discard` and trimmed weekly, while a review of the same model empty reports a fast region of about 240 GB (`docs/research/sota-measurement.md` § 3.2). {{#m1-21-drive-state}} settles it; until then, report bytes written per edge next to every time (25.0 B/edge at 32 GB and 30.7 B/edge at 8 GB for the lab prototype, by arithmetic on ADR 0026's numbers).
