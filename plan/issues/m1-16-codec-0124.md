**Question.** In our codec every gap costs at least one byte plus two control bits (10 bits), including the many gaps of 1 that BV codes as intervals. That floor is why the byte tier stays at 11.4 bits/entry on uk-2005 against BV's 2.1 (FINDINGS § C, shared machine). Lemire's Stream VByte library ships a 0124 variant (word lengths 0, 1, 2, 4 bytes). In it a consecutive neighbour costs 2 bits, and 3-byte words grow to 4. Does a block codec 2 that the encoder picks per block when smaller pay off, and on which graphs?

**What the literature says** (`docs/research/sota-storage.md` § 4, challenge 2). Nobody has measured the variant on graphs. The gain depends on the share of gaps equal to 1: large on web graphs and after a locality ordering; zero or negative on unordered social graphs.

**Widened to a census (decided 2026-11-26, `docs/research/sota-review-2026-11.md` S11, experiment F8).** The review's offline bit count (a Python script on three small graphs, input order only) found that no single coding wins every graph, and that the largest gain is in a coding no issue named. Bits per entry of the data part, codec 0 against the best other coding: lj 17.22 against 13.76 (entropy-coded hybrid-integer tokens, a zero-order bound); web-google 20.72 against 17.12 (Elias–Fano per list); roadnet-ca 12.89 against 10.39 (bit packing) and 8.11 (entropy bound). Per-block choice of codec 0 or 0124 gains 0–4.5%. The entropy rows are lower bounds, not a codec: they have no tables and no decoder. So this issue counts every candidate, in Rust, before any codec is built. **No new codec is built before the census reports.**

**Method**
- [ ] A census in Rust under `lab/` (about 300 lines, estimate), sizes only, no timing. For each block, the exact bits of:
  - codec 0 (today's format);
  - codec 2, Stream VByte 0124;
  - bit packing in groups of 32 and 128 words;
  - Elias–Fano per list;
  - length-limited canonical Huffman over hybrid-integer tokens, with per-block tables, 8- and 12-bit limits, real code lengths and table headers included.

  Report each total with the index, and the per-block minimum.
- [ ] 8 graphs: lj, orkut, twitter-sym, Friendster, roadnet-ca, web-google, LDBC graph500-22 and one bipartite graph. A web graph with locality (uk-2005 or eu-2015 from LAW) is added if the registry has it. Each in input order and in the orders of {{#m1-09-hierarchy-order}} (hier-cap64 and BP)
- [ ] Hub blocks: a block that holds one hub list is already a per-list codec choice; count 128-word bit packing on those blocks separately (input to {{#m1-17-chunked-hub-records}})
- [ ] Threshold to go further: Huffman per block at least 15% below codec 0 on at least three graphs, tables included. Only then: a lab decoder, single-thread decode rate and random-list latency against codec 0 (interleaved A/B), and one budgeted case (Friendster PageRank under an 8 GB `MemoryMax`, codec 0 against the candidate)
- [ ] For codec 2 alone: decode speed as an interleaved A/B only where the census shows it wins
- [ ] Cost written down: a second shuffle table, the decoders (scalar, SSSE3, NEON, `simd128`) kept identical, the fuzz target; a new codec byte value, which version 1 readers already refuse (`docs/spec/eg-adjacency.md` § 4, § 6)

**Done when.** A table graph × order × coding (bits per entry, index included, and the per-block minimum), decode speed where measured, and a choice of the compact tier for {{#m2-20-archival-codec}}: one coding, or none.

**Feeds.** {{#m2-20-archival-codec}}, which waits for this and for {{#m1-09-hierarchy-order}}.

**Less `unsafe` when the codec changes next (low priority; added 2026-11-25, `docs/research/README.md` R7).** `crates/everygraph-format/src/adjacency/simd.rs` marks all six `Lanes` primitives and the dispatch `unsafe`. Since Rust 1.87 (our MSRV) most `std::arch` intrinsics without pointer arguments are safe inside a `#[target_feature]` function; only loads, stores and the dispatch call stay `unsafe`, and the `Lanes` trait forces `unsafe fn` only because a trait method cannot carry `#[target_feature]` (the report's understanding of the target-feature 1.1 rules; verify before acting). If this experiment leads to a codec change, the new decoders use per-architecture free functions; not worth doing on its own (`docs/research/sota-approx-rust.md` § 3 B, challenge 10).

**Input from m1-09 (#23, exploratory).** After a locality order (hierarchy DFS or BP), gaps get smaller, so the estimate of 0124's gain over the current codec drops by 3–4 points (`lab/m1-09-hierarchy-order/results/README.md`). Measure on both the input order and a compacted order.
