---
title: Determinism in CI: hashes across thread counts and platforms
milestone: M3 · Engine and kernels
labels: type:infra, area:engine, P0, risk:medium, size:S, lab-evidence
---
**Why.** Deterministic output is a headline guarantee (DESIGN D14). The lab already showed identical results across native, wasm32, wasm64, Node and Chromium and across 1–32 threads for the simple kernels, identical Leiden/Louvain hashes at 1–32 threads, and byte-identical layout and tile files — after one thread-dependent float merge was found and fixed in the layout. Such regressions are easy to introduce.

**Scope**
- [ ] Canonical result hashing (FNV/BLAKE3 over output columns) exposed by every kernel
- [ ] CI job: each kernel on tier-1 graphs at 1, 2, 3, 8 threads and oversubscribed (32 workers on 4 cores), plus native vs wasm32; all hashes must match
- [ ] The same hashes under each execution regime (forced: in memory, edges on disk, state on disk) and under two memory budgets, and for a view run as a mask and materialized (`design/DECISIONS.md`, 2026-11-25, "What 'repeatable' promises"). Results cut short by `timeout` are exempt
- [ ] Floating point: fixed chunking and reduction order; make results bit-identical across the supported CPU architectures; an exception needs an ADR that narrows the promise of `docs/api-sketch.md` § 2.11. Sharpened 2026-11-25 (`docs/research/README.md` N2): rustc never contracts `a*b + c` into a fused multiply-add unless `mul_add` is written (checked on x86-64 `znver4`, aarch64, wasm32 and i686, `docs/research/sota-numerics.md` § 3.2), so the real hazards are std transcendentals, `powi`, run-time-dispatched SIMD, `HashMap` order, NaN and −0.0 bits, and FTZ. The rule list, each enforced as stated (`docs/research/sota-numerics.md` § 4):
  - **R1** result-bearing arithmetic uses only + − × ÷ `%` `sqrt`, explicit `mul_add`, `as` casts and comparisons (IEEE-exact in Rust, RFC 3514);
  - **R2** no std transcendental (`sin cos tan asin acos atan atan2 sin_cos exp exp2 exp_m1 ln log log2 log10 ln_1p powf powi cbrt hypot sinh cosh tanh asinh acosh atanh gamma ln_gamma erf erfc`, f32 and f64) outside the pinned math module ({{#m2-26-core-math}}); `powi(2)` → `x*x` — clippy `disallowed-methods` in the shared list of {{#m2-18-portability-lint-shared}};
  - **R3** no `mul_add_relaxed`, `algebraic_*`, fast-math intrinsics, `std::arch` FMA or approximate (`rsqrt`, `rcp`) intrinsics, run-time CPU dispatch (`is_x86_feature_detected!`) in float code, and no `cfg(target_feature)` choice of float algorithm or lane count — clippy `disallowed-methods`/`-macros`, review;
  - **R4** every reduction tree is a function of the data and source constants only, never of thread count, budget, regime, I/O buffer, decode batch or SIMD width — order probes (R15b);
  - **R5** sums whose order depends on the schedule (atomics, hash or bucket aggregation, push contributions) are integer or fixed point, never float ({{#m4-02-weights-resolution}}) — review, weighted hashes (R15a);
  - **R6** global scalars use the exact accumulator of {{#m2-26-core-math}} — review, probe;
  - **R7** no `Iterator::sum`/`product` on floats in result code (it starts from −0.0: an empty list gives −0.0, a loop from 0.0 gives +0.0); `total_cmp` where ±0 or NaN can tie (`f64::max` "may return either input non-deterministically") — a core float-fold helper and review, since clippy cannot ban `Iterator::sum` for floats only;
  - **R8** no `HashMap`/`HashSet` with a randomly seeded hasher (std `RandomState`, hashbrown/foldhash and ahash defaults) whose iteration order reaches a result; fixed-seed hashers or sorted output — clippy `disallowed-types`, `deny.toml`;
  - **R9** all randomness from the counter-based RNG of {{#m2-27-counter-rng}} with its documented key schema; no entropy-seeded or stateful-stream RNG, no `usize` sampling, no `rand_distr` float distributions — `deny.toml` bans `fastrand`, `getrandom` and `rand` outside dev-dependencies;
  - **R10** NaN and −0.0 canonicalized in results, derived sections and result hashes (the helper of {{#m2-26-core-math}}); results are never NaN by spec;
  - **R11** the supported targets below; `relaxed-simd` is a `compile_error!` in wasm builds (FMA "fused or not" and NaN/±0 min/max are implementation-defined there);
  - **R12** an FTZ/DAZ probe at kernel entry when called from a foreign host: the Python module ({{#m6-01-python-api}}) tests `black_box(f64::MIN_POSITIVE) / 2.0 != 0.0` on the calling thread and once per worker, and refuses (or resets in scope) with the reason. A shared library linked with `-ffast-math` sets FTZ/DAZ for the whole process on load, and MXCSR is per thread, so the sequential path could differ from the workers (Dolan-Gavitt 2022, search summary only). Test: load a test `.so` linked with `-ffast-math` in CI and run PageRank on a graph with subnormal weights;
  - **R13** text ↔ float by `str::parse` and `{}` (shortest round trip); never `{:.N}` in cache keys or provenance;
  - **R14** pinned versions: the math crate at an exact version and the rule-list version (`numerics=N`) in provenance;
  - **R15** the tests below
- [ ] Supported platforms, as written into D14's text: x86-64 (any `target-cpu`), aarch64, i686 with SSE2, wasm32 without `relaxed-simd`; i586/x87 and 32-bit ARM NEON float SIMD are excluded (not IEEE-compliant in Rust, RFC 3514)
- [ ] (R15a) Hash tests on **weighted** tier-1 graphs with wide-range weights (log-uniform over 2^-20…2^20) as well as unweighted ones: on unweighted graphs every sum is a sum of integers, exact in any order, so a reduction-order bug passes (Leiden on tier-1 graphs would pass with any order today)
- [ ] (R15b) FPRev-style order probes (Xie et al., ATC'25): an input of ones with one +M and one −M, run through every reduction primitive and per-node accumulator at threads {1, 2, 3, 8, 32 on 4}, chunk sizes {64, 65,536}, every regime and two budgets; the revealed summation tree must equal the specified one. O(n²) calls, so n ≤ 1,024. First targets: `core::par::map_ranges`'s fold and the PageRank pull accumulator
- [ ] (R15c, R15d) The golden vectors of {{#m2-26-core-math}} and the reference vectors of {{#m2-27-counter-rng}} run on all four targets
- [ ] (R15e) Cross-platform identity by a hash of the full output, not by sum and maximum: native ↔ wasm32 (Node) and x86-64 ↔ aarch64 (qemu-user on the self-hosted runner) for PageRank, Leiden and the layout. The evidence ADR 0014 cites for platforms is weak: PageRank and components were compared across native and wasm by sum and maximum, not by a hash, and Leiden was run on x86-64 only (`docs/research/sota-numerics.md` § 3.1); this item is what turns "any platform" into a tested claim
- [ ] The `fast` (non-deterministic) modes are labelled as such in output provenance
- [ ] Large-graph references: the `ldbc` profile proposed by {{#m1-20-ldbc-graphalytics}} (LDBC Graphalytics reference outputs for BFS, WCC, PageRank in f64, CDLP, LCC, SSSP), run in the nightly job, in RAM and under a budget below the graph's size (added 2026-11-25, `docs/research/README.md` B12)
- [ ] A scheduled nightly workflow that runs `oracle/run-nightly.sh` (fetches tier 1, checks all golden files, nightly corpus, seeded bugs) and opens an issue when it fails; billed minutes stated (the script took 18 min on the lab machine)

**Acceptance**
- A PR that makes a reduction order depend on the thread count fails CI — shown on a weighted graph and by an order probe, since on unweighted graphs it would pass
- Adding a std transcendental, an entropy-seeded RNG or a randomly seeded `HashMap` to a result crate fails the lint; the lists flag the lab's `lab/e-map/gmap/src/layout.rs` l. 139–140 (`cos`/`sin`) and `crates/everygraph-oracle/src/generators.rs` l. 282 (`powf`)

**Done by the first pull request (Part of #54).** `crates/everygraph-determinism`: the build, every kernel of `everygraph run`, weighted `PageRank`, eigenvector and SSSP, and Leiden at 1, 2, 3, 8 and 32 threads, two chunkings, four sources and repeated runs (sampled on every pull request; every combination nightly in `.github/workflows/determinism.yml`); R15a on weighted planted graphs; R15b order probes of `par::map_ranges` and the edge-map reduction; Miri `-Zmiri-many-seeds=0..16` on the tests of `par`, nightly. Both halves of the first acceptance criterion were shown by mutations (the pull request). Three findings for Leiden in `tests/leiden_views.rs`, decided by {{#m4-15-determinism-contract}}: a view as a mask and materialized, and nodes without edges, now give the same communities (the tests pass); renumbering the ids (`compact --order`) is another input, which D14 does not cover (the test is removed with the claim).

**Left.** Canonical result hashes exposed by every kernel; native ↔ wasm32 for Leiden and the layout, and x86-64 ↔ aarch64 by a full hash (R15e); the forced regimes and two budgets in the grid and in the probes (after {{#m3-02-planner}} and {{#m3-03-semi-external}}); the `fast` label in output provenance; R12 (FTZ/DAZ probe); the LDBC references nightly; the nightly `oracle/run-nightly.sh` workflow; the second acceptance criterion re-checked against the numerics lint.
